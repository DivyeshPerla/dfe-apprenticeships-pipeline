The answer this data gives you is 24× too big

Building a production data pipeline on Google Cloud — and the reason it needed to exist.

Sai Teja Sunku · data engineering case study

Speaker notes

Open on the number. Don't explain the dataset yet — the audience doesn't need to know or care what it is. The claim is that a reasonable-looking query on real public data returns something 24 times wrong, and everything after this earns that.

02 · Setup

I picked a public dataset at random

UK government statistics. A free API, no key, seventeen tidy columns, fifty thousand rows. The kind of thing that looks like an afternoon's work.

Before writing any pipeline code, I profiled it. It was lying in four different ways — none of which show up in the schema, and none of which cause an error.

The dataset is incidental. The failure modes are not — they appear in most real-world source data.

Speaker notes

Say explicitly that the dataset was chosen arbitrarily and that no domain knowledge is needed. What's being demonstrated is the method: profile before you build, and design for what you find.

03 · The problem

One SUM. Three answers.

QueryResult
The obvious one — SUM over every row8,484,310
Correct: only rows at the true detail level353,500
The publisher's own stated total353,500

Four-fifths of the rows are subtotals mixed in with the detail. The obvious query counts the same records once for every subtotal they appear in.

It doesn't error. It returns fast. The number looks plausible.

Speaker notes

The silent failure is the point. Nothing warns you. This is the case for modelling the grain explicitly and testing it, rather than trusting that a query which runs is a query which is right.

04 · The problem

And three more like it

  • The numbers aren't numbers. Up to a quarter of the values are withheld for privacy, encoded as text inside the numeric columns. Cast them naively and they vanish; fill them with zero and you've invented data.
  • History gets rewritten. The publisher has issued six versions, quietly restating figures in each. Any analysis pinned to one download is wrong the moment the next lands.
  • Everything is rounded. Every published figure is a multiple of ten, so the parts can never exactly equal the whole.

Each one silently corrupts a result rather than failing loudly. That is what the pipeline is built to prevent.

Speaker notes

Keep this brisk — it's a list, not a deep dive. The audience only needs to accept that the data is genuinely hostile before seeing the architecture.

06 · The build

Where the problems get handled

ProblemHow the pipeline handles it
Subtotals mixed with detailEvery row tagged with its aggregation level; the published views are pre-filtered so the wrong answer isn't reachable
Withheld values as textSplit into a number and a reason — never zero-filled
Rewritten historyAll six versions retained; the warehouse can answer "what did they report in January?"
RoundingReconciliation tests use a tolerance derived from the rounding, not an invented fudge factor

Speaker notes

The key design idea: the correct answer is the easy one. A consumer of the published views can't reproduce the 24× error by accident, because the guardrail lives in the model rather than in the analyst's discipline.

07 · The build

It only runs when there's work

The source updates roughly quarterly. A daily pipeline would redo identical work about ninety times per release.

Instead a small job checks whether anything actually changed, and the workflow branches on the answer.

08 · Rigour

The bug the tests caught

Twenty-six automated tests run with every build. One of them earned its place during this project.

After an unrelated change I re-ran the pipeline to confirm nothing had broken. A test failed. The date had rolled over between runs, and because raw data is never overwritten, the same source version had been stored twice — so every figure was being counted twice downstream.

102,596
rows seen downstream — doubled
51,298
after the fix — correct

The test stopped the run before anything reached the published layer.

Speaker notes

The strongest slide — don't rush it. A latent bug that only appears when a date changes, caught automatically, in production, on its first real occurrence. It's evidence the tests aren't decorative. Worth noting it surfaced only because the earlier change was verified rather than assumed.

09 · Governance

Compliance checked, not claimed

A script verifies eighteen controls against the live cloud environment and fails the build if any regress — data location, public exposure, credentials, access scope, retention, privacy, audit trail.

It found two real problems:

  • Data was leaving the country. The build tool silently staged source files in a US region, against a UK-only requirement.
  • An over-privileged default account. Cloud providers grant broad write access to a default identity — and the build was using it. Revoking it naively would have broken the pipeline; the fix was a purpose-built identity.
Screenshot 7

Terminal — the verification script, ending 18 passed, 0 failed.

Speaker notes

Both findings were invisible to a written policy and obvious to an automated check. The second is the better story: the obvious remediation would have broken the build, so knowing why the easy fix is wrong matters more than reporting a clean pass.

11 · Payoff

What the data actually showed

Once it could be trusted — the composition of the market inverted over eight years.

Total volume barely moved. The mix inverted. Anyone watching headline numbers alone would conclude the market was flat and stable.

Speaker notes

This is the argument for the whole build: the interesting finding was invisible in the headline figures and only became visible once the data could be trusted at detail level. Mention the regional spread if there's time — the shift is national but London moved half again as far as the slowest region.
