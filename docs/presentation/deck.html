02Act I · The problem

Seventeen columns of government statistics. Four traps.

Free API, no key, clean CSV. It looks like a afternoon's work.

Trap 1 The numbers are not numbers. Measure columns carry disclosure markers — low, c, z. Up to 23% of counts are withheld. Cast naively and they become null; coalesce them and you have invented zeros.

Trap 2 80% of rows are subtotals. Every filter dimension carries its own Total member. Only 10,066 of 51,298 rows are true detail grain.

Trap 3 History gets rewritten. Six published versions; rows added, removed and silently restated. An analysis pinned to one download is wrong the moment the next lands.

Trap 4 Everything is rounded to 10. All 42,045 published values are exact multiples of ten — so sums of parts can never equal a published whole.

Speaker notes

Land the point that none of these are documented in a way you'd catch by reading the schema. Each was found by profiling the data before writing a line of pipeline code. That order — profile first — is the actual lesson.

06Act II · The pipeline

Bronze: immutable and replayable

Raw extracts land in Cloud Storage partitioned by source version and extraction date, and are never modified.

  • Every load writes a manifest with row count and SHA-256 — all six versions reconcile exactly against the API's own reported totals.
  • Everything lands as STRING by design. Typing here would silently destroy the suppression markers.
  • Hive partitioning means version and ingest_date become queryable columns for free — derived from the object path, no ingestion code.

09Act II · The pipeline

It only works when there's work to do

The source publishes roughly quarterly. A daily pipeline that reloaded regardless would repeat identical work about ninety times per release.

10Act III · Rigour

Twenty-six tests, two of which are opinions

Most are structural — uniqueness, referential integrity, accepted values. Two encode business judgement.

  • Current records must equal the latest published version. If the SCD-2 validity logic drifts by a single row, this fails immediately.
  • Detail grain must reconcile to the publisher's own total within 0.1%. Not equality — because everything is rounded to 10, summing ~122 rounded values can never equal an independently rounded total. Expected error is about 5√n ≈ 55; observed is 0–90. The tolerance is loose enough to absorb rounding and tight enough that a real aggregation bug, which would be 24×, fails loudly.

Models and tests run together via dbt build, so a failing test blocks publication to gold rather than reporting it afterwards.

Speaker notes

The tolerance test is worth dwelling on: the naive instinct is to assert equality, watch it fail, and hardcode a fudge factor. Deriving the threshold from the rounding regime is the difference.

11Act III · Rigour

The bug the tests caught

This one wasn't planned. It happened during this build, in production.

After a routine IAM change I re-ran the pipeline to confirm nothing had broken. It failed — but not on permissions. A uniqueness test failed.

The calendar date had rolled over between runs. Bronze is append-only, so re-extracting the same version landed a second ingest_date partition beside the first — and the external table reads every partition. Silver was seeing all 51,298 rows twice.

LayerRows for v2.0.2
Bronze (all partitions)102,596duplicated
Silver, after fix51,298resolved to latest extraction
Gold, current51,298correct

The test stopped the run before anything reached gold. A latent idempotency bug that only surfaces when a date changes, caught by the safety net, in production, on its first real occurrence.

Speaker notes

This is the strongest slide in the deck — don't rush it. It's evidence the tests aren't decorative. Note also that it was only found because the IAM change was verified rather than assumed; the discipline found the bug, not luck.

14Act IV · Compliance

Two things the checks found

Both were real, both were invisible to a written policy, both are fixed.

Finding 1 Data was leaving the UK. gcloud builds submit silently creates a staging bucket in the US. Nine source archives — including a dbt seed — had staged there, contradicting the residency posture of every other resource.

Fixed with an in-region staging bucket pinned in the deploy script. The US bucket is deleted; the check now fails if any bucket sits outside the region.

Finding 2 An over-privileged default identity. Google grants the default compute service account project-wide roles/editor at project creation — and Cloud Build was using it.

The naive fix breaks the build. The correct one is a dedicated build identity holding only registry write, source read and log write. Verified by running the pipeline afterwards — which is exactly how the idempotency bug on slide 11 surfaced.

Speaker notes

Finding 2 is the better story: the obvious remediation would have broken the pipeline. Naming why the easy fix is wrong demonstrates more than reporting a clean pass would.

15Act V · What the data says

The market didn't shrink. It moved upmarket.

Volumes are broadly flat across eight years. The composition inverted.

Share of starts by level, England. 2025/26 is provisional (three quarters).

Intermediate 43.0% → 17.3%. Higher 12.8% → 41.0%. Advanced barely moved — which is what makes this clean: it is not a general drift, it is Intermediate giving way directly to Higher.

Speaker notes

The commercial reading: a provider watching only headline volumes concludes the market is flat and stable. It isn't. Demand didn't fall, it changed level — and provision built for Intermediate delivery is chasing a segment that has lost three-fifths of its share.

18Act V · What the data says

What this data cannot tell you

Naming the limits is part of the analysis.

  • Not completion rates. Dividing same-year achievements by same-year starts looks like a completion rate and isn't — apprenticeships run one to four years, and there is no cohort linkage between a start and the achievement it eventually produces. The 2017/18 figure of 0.735 is a large pre-reform cohort completing against a shrunken post-reform intake. That's a fifth trap, and the honest response is to not compute the ratio.
  • No individual provider detail — provider type only, so no benchmarking.
  • No sector or subject split — this extract carries level, age, funding and provider type.
  • No sub-regional geography — region is the finest grain available.
  • 2025/26 is provisional — three quarters, excluded from every trend conclusion and flagged as such throughout the warehouse.
Speaker notes

This slide does more for credibility than any chart. Anyone who knows this data will be waiting to see whether completion rates were computed naively — saying explicitly that they can't be is the answer they're listening for.

19Close

What I'd do differently

  • Confirm the suppression codes against the published methodology first. Their meanings were inferred from the data's own behaviour. That inference drives a whole dimension table, and it should have been checked against the source documentation on day one.
  • Add CI. The tests and compliance checks run on demand; they should run on every push. That's an afternoon's work and it's the obvious gap.
  • Revisit dbt versus Dataform. dbt was chosen for portability and because it is the industry standard. Dataform is native, free, and would have removed a container image.
  • Ask for the raw ILR. Almost every limitation on the previous slide dissolves with learner-level data — at the cost of a genuine UK GDPR scope, which this project deliberately does not have.
Speaker notes

Have this slide ready but be willing to skip it for time. If asked "what would you improve", this is the answer — offering it unprompted signals the self-assessment was done.
